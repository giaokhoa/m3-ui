Material typography is a system of semantic text roles. Choose a role for the job the text performs, then keep that role's typeface, size, line height, weight, and tracking together as one contract instead of treating the scale as a menu of unrelated CSS values.

## Type roles and hierarchy

`m3-ui` exposes the complete 15-role baseline Material type scale: five role families, each with large, medium, and small variants.

| Family | Intended use | Public roles |
| --- | --- | --- |
| Display | The largest, most prominent text for major moments in a layout. | `displayLarge`, `displayMedium`, `displaySmall` |
| Headline | Short, important text that establishes section or content hierarchy. | `headlineLarge`, `headlineMedium`, `headlineSmall` |
| Title | Shorter, medium-emphasis titles for named surfaces or content groups. | `titleLarge`, `titleMedium`, `titleSmall` |
| Body | Reading text and longer-form content. | `bodyLarge`, `bodyMedium`, `bodySmall` |
| Label | Compact action, annotation, and component-supporting text. | `labelLarge`, `labelMedium`, `labelSmall` |

<GuidanceCallout title="Choose roles by meaning, not by pixel size">
  Start with the content hierarchy and the role's intended use. Do not pick a role only because its current rendered size happens to fit a mockup; that couples the document hierarchy to one token value instead of the Material type system.
</GuidanceCallout>

## A type role is one contract

Each role resolves five coordinated properties:

- **Typeface role** — a semantic `plain` or `brand` family reference supplied through the active theme.
- **Font size** — the role's scale position.
- **Line height** — vertical rhythm paired with that size.
- **Font weight** — the intended emphasis within the role.
- **Tracking** — letter spacing paired with the rest of the role metrics.

Treat those properties as a unit. Mixing, for example, the size from one Material role with the tracking or line height from another creates a new application-specific style rather than using the canonical role.

Concrete metrics remain owned by `packages/tokens` and flow through generated `@m3-ui/tokens` output. Documentation intentionally names semantic roles instead of duplicating canonical numeric values in MDX.

## Standard and emphasized roles

The baseline Material hierarchy above is the default. Current AndroidX Material3 `Typography` also exposes an emphasized counterpart for every baseline role. `m3-ui` represents that capability with the same 15 public role names plus an explicit `emphasis` choice.

  The baseline hierarchy is grounded in Material 3 typography guidance. The emphasized counterparts are tracked as current AndroidX Material3 / M3 Expressive API evidence and canonical repository token evidence. `m3-ui` does not silently treat Compose-only vocabulary as a separate normative Material role family, and cross-source differences should remain visible rather than being normalized in prose.
</GuidanceCallout>

Standard remains the default. Opt into `emphasized` only where the stronger style supports hierarchy or draws attention intentionally; availability of emphasized tokens is not a reason to replace the baseline scale globally.

## Apply roles with the public helpers

Use `getMaterialTypeCssProperties()` when a Material role should be applied directly to a React `style` prop. Use `getMaterialTypeStyle()` when application code needs the resolved Material role as data before applying or composing it.

```tsx
import {
  getMaterialTypeCssProperties,
  getMaterialTypeStyle,
} from '@m3-ui/ui';

const leadStyle = getMaterialTypeStyle('bodyLarge');

export function ArticleIntro() {
  return (
    <section>
      <h2 style={getMaterialTypeCssProperties('headlineMedium')}>
        Account settings
      </h2>
      <p style={leadStyle}>
        Manage the settings that apply to your account.
      </p>
    </section>
  );
}
```

Pass `emphasized` as the second argument when the emphasized counterpart is intentional:

```tsx
<strong
  style={getMaterialTypeCssProperties(
    'labelLarge',
    'emphasized',
  )}
>
  New
</strong>
```

Both helpers consume public role names and generated token values. Application code does not need to import typography tokens directly or reproduce a role's metrics manually.

## Typeface ownership and theming

The resolved `fontFamily` points at the theme's semantic typeface variables, such as `--font-family-plain` and `--font-family-brand`. This keeps the role contract stable while the active theme owns the actual font family.

Typography helpers therefore answer **which Material role to render**; theming answers **which typeface fulfills the semantic family role**. Component and foundation documentation should not bake a separate font stack into each usage example.

## Typography is not document semantics

Material type roles describe presentation and hierarchy; they do not replace HTML semantics. Keep headings as heading elements, paragraphs as paragraphs, form labels as labels, and interactive controls as their correct browser elements, then apply the appropriate Material type role to those elements.

In particular, a Material `label*` role does not turn arbitrary text into an HTML `<label>`, and a `headline*` role does not determine the document heading level by itself.

The docs application follows the same boundary: Markdown keeps native document structure while the MDX runtime maps those elements to Material type roles. There is intentionally no public `Typography` or `Prose` component created solely for documentation styling.

## Code text is a web/docs adaptation

Material does not define a dedicated code type role. Documentation code uses a monospace browser/docs adaptation while surrounding surfaces, hierarchy, and semantic text continue to use Material roles. That adaptation stays local to `apps/docs` and is not presented as part of the Material type scale.

## Provenance and drift boundary

- **Material 3 specification/guidance** defines the typography system, role hierarchy, and design intent used on this page.
- **AndroidX Compose Material3** is implementation/reference evidence for the current `Typography` API vocabulary, including emphasized counterparts.
- **`m3-ui`** exposes the web-facing `MaterialTypeRole`, `MaterialTypeEmphasis`, `getMaterialTypeStyle()`, and `getMaterialTypeCssProperties()` contract backed by canonical generated tokens.
- **Web/document semantics** remain native HTML concerns and are composed with Material visual roles rather than replaced by them.
- **Material Web or Figma evidence**, when audited elsewhere in the repository, is implementation evidence only; it does not override Material guidance or justify silently rewriting role definitions here.

When these sources differ in vocabulary or availability, keep the difference explicit. Do not invent a merged typography model in documentation, and do not hand-copy concrete metrics to hide token or source drift.
