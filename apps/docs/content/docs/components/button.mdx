## Usage and variant hierarchy

Material's Button family has five common variants. Choose the variant for the action's emphasis; do not choose one only because its decoration looks more prominent.

| Public component | Material guidance | Typical use |
| --- | --- | --- |
| `Button` | Filled, high emphasis | Important final or primary actions such as Save, Confirm, or Join now |
| `FilledTonalButton` | Middle ground between filled and outlined | A significant or lower-priority action that needs more emphasis than an outline |
| `OutlinedButton` | Medium emphasis | Important but non-primary alternatives such as Back or Cancel |
| `TextButton` | Lowest emphasis | Supplementary and low-priority actions, especially alongside stronger actions |
| `ElevatedButton` | Tonal-style container with elevation | Use when the action needs visual separation from a patterned or difficult background, not simply to make it look more important |

### Labels

Material guidance says a Button label should describe the action that will occur. Prefer concise action wording such as **Save**, **Confirm**, **Next**, or **Back** over labels that do not explain the result.

### Icons

An icon is optional. Use it when it helps communicate the action or draws useful attention to it; keep visible text as the stable action label.

## Do and don't

<GuidanceCallout title="Material — Do" kind="guidance">
  <ul>
    <li>Choose Filled, Tonal, Outlined, Text, or Elevated according to the action emphasis.</li>
    <li>Use a label that describes the action that will happen when the Button is activated.</li>
    <li>Add an icon only when it helps clarify the action; keep the label as the primary content.</li>
    <li>Use Elevated when the Button needs separation from a patterned or visually difficult background.</li>
  </ul>
</GuidanceCallout>

<GuidanceCallout title="Material — Don't" kind="caution">
  <ul>
    <li>Do not use Elevated only to make an action look more important; Material recommends limiting elevation to avoid excessive shadow.</li>
    <li>Do not give actions with different priorities the same emphasis when that obscures the action hierarchy.</li>
    <li>Do not choose a variant only for its color or decoration; the variant should communicate action priority and context.</li>
  </ul>
</GuidanceCallout>

<GuidanceCallout title="m3-ui / web — Do" kind="web">
  <ul>
    <li>Use `onPress` and let React Aria own keyboard, pointer, focus-visible, and disabled semantics.</li>
    <li>Use `size`, `buttonShapesForSize()`, variant components, and theme tokens instead of copying padding, radius, elevation, or state colors.</li>
    <li>Use a link or anchor for navigation; use Button for an action.</li>
    <li>Use `IconButton` when the action is intentionally icon-only, and provide an accessible label.</li>
  </ul>
</GuidanceCallout>

<GuidanceCallout title="m3-ui / web — Don't" kind="caution">
  <ul>
    <li>Do not attach an independent click handler to child content inside a Button; the root Button must remain the single action owner.</li>
    <li>Do not override geometry or state presentation in application CSS to imitate another Button variant.</li>
    <li>Do not infer Android precision-pointer compaction from `pointer: fine`, hover capability, or the current pointer event.</li>
  </ul>
</GuidanceCallout>

## Expressive sizes

The public `size` API exposes `extraSmall`, `small`, `medium`, `large`, and `extraLarge`. Size changes the Material geometry, icon scale, spacing, and label type role as one contract; avoid changing those dimensions independently.

<LiveExample example="button-sizes" title="Material expressive Button sizes" sourceInitiallyOpen />

Omitting `size` uses `small`, matching the current Material 3 Design Kit component-set default. The legacy baseline remains in the token source as audited Compose-classic / Material-Web-runtime evidence; it is not the public React default.

## Round and Square shapes

The current Material 3 Design Kit publishes both Round and Square Button types for every expressive size. Use the audited helper instead of copying corner radii.

<LiveExample example="button-shapes" title="Round and Square Button shapes" sourceInitiallyOpen />

`buttonShapesForSize(size)` uses Round. Pass `'square'` as the second argument for the size-specific Square container. Both forms keep the audited pressed-shape target for that size.

## Behavior and states

React Aria owns the current browser interaction state. Material tokens, ripple, shape, color, elevation, and motion own presentation for hover, keyboard focus, press, and disabled state.

<LiveExample example="button-states" title="Enabled and disabled Button states" sourceInitiallyOpen />

The Button is the single action owner. Do not add a second press/click engine inside the content tree.

## Accessibility

`Button` uses browser button semantics with keyboard activation, disabled handling, and focus-visible behavior supplied by React Aria. Use visible action text that describes the result of activation.

`startIcon` and `endIcon` are decorative slots and are kept out of the accessibility tree so the visible action label remains the stable accessible name. When an action must be icon-only, use the dedicated [Icon button](/docs/components/icon-button) family and provide an accessible label.

## Material fidelity and web adaptation

<MaterialParity component="button" />

Material 3 is authoritative for Button hierarchy, visual variants, shape, state treatment, and expressive sizing. Browser/React Aria semantics intentionally supply native web activation, pointer hover, keyboard focus, and event lifecycles rather than mechanically porting Compose runtime primitives.

The current Compose precision-pointer policy is intentionally not mapped to a CSS media query: its Android trigger depends on an enabled feature flag and physical keyboard + mouse device inventory, which is not equivalent to `pointer: fine` on the web. Choose `size` explicitly when a product needs a denser web control policy.
