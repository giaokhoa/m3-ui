## Component guides

These pages document the public React API through the Material contract: family, variants, states, accessibility, Compose mapping, and intentional web adaptations.

### Actions

- [Button](/docs/components/button) — five Material button variants plus expressive sizes and interaction states.
- [Icon button](/docs/components/icon-button) — action and toggle families across audited variants, sizes, widths, and shapes.
- [FAB](/docs/components/fab) — icon-only and extended floating actions, audited sizes/elevation, and explicit cross-source compatibility variants.
- [Chip](/docs/components/chip) — assist, suggestion, filter, and input chip families with action versus selection semantics kept distinct.

### Input and surfaces

- [Text field](/docs/components/text-field) — filled and outlined fields, supporting content, validation, and native input behavior.
- [Card](/docs/components/card) — filled, elevated, and outlined surfaces with an explicit semantic-role boundary for interactive cards.
- [Dialog](/docs/components/dialog) — Material modal composition, scrim, actions, theme portals, and focus semantics.
- [Lists and list items](/docs/components/list-item) — passive, action, single-radio, and multiple-checkbox rows with one-, two-, or three-line Material geometry.
- [Menus](/docs/components/menu) — anchored menus, sections, items, and a read-only exposed-menu form with React Aria focus semantics.
- [Badges](/docs/components/badge) — dot/content badge geometry plus explicit application-owned accessible status wording.
- [Dividers](/docs/components/divider) — horizontal and vertical semantic separators with token-backed Material defaults.

### Selection controls

- [Checkbox](/docs/components/checkbox) — checked, unchecked, indeterminate, disabled, and interaction states.
- [Radio button](/docs/components/radio-button) — single-selection groups, labels, validation, and keyboard semantics.
- [Switch](/docs/components/switch) — on/off state, optional thumb content, disabled treatment, and theme focus indication.
- [Slider](/docs/components/slider) — single and range values, audited sizes, accessible thumbs, and explicit web adaptations for ticks and value indicators.

### Grouped controls

- [Tabs](/docs/components/tabs) — primary/secondary tab lists, fixed or scrollable presentation, and application-owned panel content.
- [Segmented buttons](/docs/components/segmented-button) — single-choice radio semantics and multi-choice checkbox semantics kept distinct.
- [Split button](/docs/components/split-button) — independent leading/trailing actions with disclosure or toggle state while menu content remains application-owned.
- [Button group](/docs/components/button-group) — standard action groups with local overflow plus connected single/multiple selection groups.

### Discovery and feedback

- [Search bar](/docs/components/search-bar) — collapsed search input with docked or full-screen expanded surfaces and an application-owned data boundary.
- [Progress indicators](/docs/components/progress-indicator) — standard and M3 Expressive wavy progress with determinate, indeterminate, and explicit Web compatibility behavior.
- [Loading indicator](/docs/components/loading-indicator) — expressive Material shape morphing in contained and uncontained forms.
- [Snackbar](/docs/components/snackbar) — transient-message surface, live-region semantics, actions, and an explicit host/timeout boundary.
- [Tooltips](/docs/components/tooltip) — plain tooltip semantics kept distinct from interactive rich-tooltip dialog semantics.

## Documentation rule

A component page should describe behavior that exists in `@m3-ui/ui`; it must not become a second implementation of the component. Live previews use the public package, and Material measurements remain sourced from canonical generated tokens rather than documentation CSS literals.

Cross-source compatibility APIs are labeled as such instead of being presented as Compose-only Material contracts.

## Layout boundary

Component documentation does not define adaptive window classes, pane directives, navigation switching, or scaffold behavior. Layout documentation will consume the dedicated `@m3-ui/ui/layout` subsystem instead of creating a docs-only responsive model.
