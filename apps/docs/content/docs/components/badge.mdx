Badges add compact status or count information to another element. Material defines the dot/content visual forms and anchor positioning; the application decides what the badge means to users and assistive technology.

[Material 3 badges](https://m3.material.io/components/badges/overview)

```tsx
import { Badge, BadgedBox, IconButton } from '@m3-ui/ui';

<BadgedBox badge={<Badge aria-hidden="true">3</Badge>}>
  <IconButton aria-label="Notifications, 3 unread">
    <NotificationsIcon />
  </IconButton>
</BadgedBox>
```

## When to use

Use a badge for brief supplementary status/count information that belongs to an anchor. Do not use a badge as the only place to put important explanatory text or an action.

A dot can indicate a meaningful binary status only when surrounding context makes that meaning clear. The component does not guess that a dot means “new”, “online”, or “unread”.

## Dot and content forms

Omitting children selects the Material dot form. Supplying content selects the content badge form and typography. Canonical colors and geometry come from component tokens; `containerColor` and `contentColor` are deliberate overrides, not a second token source.

## Positioning

`BadgedBox` positions the badge at the logical top-end of its anchor, so directionality remains correct in LTR/RTL layouts. It is a positioning primitive only: it does not change the anchor's interaction semantics or merge accessibility trees.

## Accessibility

Decide whether the badge meaning should be exposed through the badge itself or through the anchor's accessible name/status relationship.

When a visual count duplicates wording already included in an icon button's accessible name, hide the badge from assistive technology to avoid duplicate announcements. When the badge is standalone meaningful status, give it appropriate accessible text/semantics from the application context.

Do not make `Badge` infer wording such as “unread notifications”; only the application knows the domain meaning.
