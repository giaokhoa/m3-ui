Date pickers let users choose a Gregorian calendar date or date range using Material calendar and segmented date-input surfaces. The public value model is date-only and intentionally avoids timezone-bearing JavaScript `Date` state.

[Material 3 date pickers](https://m3.material.io/components/date-pickers/overview)

</ComponentPreview>

```tsx
import { DatePicker, type DatePickerDate } from '@m3-ui/ui';

const [date, setDate] = useState<DatePickerDate | null>('2026-08-29');

<DatePicker value={date} onChange={setDate} />
```

## When to use

Use `DatePicker` when users choose one calendar date and `DateRangePicker` when the task needs an inclusive start/end range. Prefer direct text fields only when the application does not benefit from calendar or segmented date interaction.

## Date-only state

`DatePickerDate` is an ISO calendar-date string such as `2026-08-29`. Selection state never becomes a JavaScript `Date`; UTC may be used internally only as an `Intl.DateTimeFormat` transport for locale formatting.

This avoids accidental timezone shifts when a value represents a calendar date rather than an instant. Public date helpers preserve the same date-only contract.

## Single and range selection

`DateRangePicker` publishes `{ start, end }` date-only values. Range drafts that are incomplete or reversed remain local until valid rather than corrupting application state. `isDateUnavailable` can keep a date navigable/focusable while preventing selection, and `yearRange` constrains supported dates.

## Calendar and input modes

Calendar mode uses React Aria Calendar/RangeCalendar semantics. Input mode uses React Aria DateField/DateInput/DateSegment primitives while preserving the same public ISO date-only state.

React Aria owns segment ordering, keyboard editing, focus movement, placeholder behavior, and field validation. Material owns the calendar/input surface, typography, state treatment, and selection visuals.

`locale` controls date presentation; `firstDayOfWeek` can override the locale default when the product has an explicit convention.

## Modal and docked presentation

`variant="modal"` selects the Material **modal-picker surface style** only. It does not create a browser overlay, scrim, focus trap, Escape lifecycle, or focus restoration.

Compose it with `Dialog` when the picker must behave as a real browser modal:

```tsx
<DialogTrigger>
  <Button>Choose date</Button>
  <DialogOverlay>
    <Dialog aria-label="Choose date">
      <DatePicker />
    </Dialog>
  </DialogOverlay>
</DialogTrigger>
```

`variant="docked"` keeps the picker in the local composition and follows its documented docked-mode behavior. Surface styling and modal lifecycle are deliberately separate concerns.

## Validation and errors

Manual input validation uses the public React Aria-backed field contract plus application rules. Use `errorMessage` for user-facing validation text. Do not turn date-format parsing or unavailable-date rules into hidden timezone conversions.

## Accessibility

Calendar/date-field semantics, keyboard navigation, date segments, and unavailable states are owned by React Aria. A modal composition must additionally provide Dialog labeling and let Dialog own modal focus/dismissal behavior.

Ensure validation errors are textual and connected to the relevant picker/input state. Do not rely only on selected color or disabled styling.
