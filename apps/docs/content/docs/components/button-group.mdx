Button groups organize related actions or connected selections while preserving the semantics of the controls inside them. `m3-ui` exposes two intentionally different contracts: standard independent actions and connected selectable buttons.

</ComponentPreview>

```tsx
import { ButtonGroup } from '@m3-ui/ui';

<ButtonGroup
  aria-label="Document actions"
  items={[
    { id: 'share', label: 'Share', onAction: share },
    { id: 'export', label: 'Export', onAction: exportFile },
  ]}
/>
```

## When to use

Use a standard button group for a compact cluster of related but independent actions. Use connected selection when the grouped controls represent one selection model. Do not use a button group only to force unrelated controls into a shared shape.

For destination navigation, use the navigation component families instead of treating button-group selection as page navigation.

## Standard action group

`variant="standard"` groups independent actions and applies the audited Material expressive press behavior. If the rendered row cannot fit its local container, the group moves a suffix of actions into its own overflow surface.

Each item may select its supported Material button variant. The group measures the **local action container** with `ResizeObserver`; it does not consume `WindowAdaptiveInfo` or choose an application layout.

The overflow trigger/surface owns its local focus and dismissal behavior. This is component-local overflow, not adaptive navigation.

## Connected selection

`variant="connected"` joins selectable buttons into a connected Material shape and requires an explicit `selectionMode`.

Single selection uses one-of-many radio semantics:

```tsx
<ButtonGroup
  aria-label="Time range"
  variant="connected"
  selectionMode="single"
  defaultSelectedKey="week"
  items={ranges}
/>
```

Multiple selection uses independent toggle-button semantics with `selectedKeys` or `defaultSelectedKeys`. Do not collapse the two modes into one generic selected-state description: their accessibility and interaction models are different.

## Expressive behavior

For standard groups, pressed-width redistribution follows the audited Material/Compose behavior while clamping growth so neighboring content cannot collapse. Connected groups instead preserve their selected/unselected color and corner-state contract.

All group sizes reuse the public Material button size vocabulary rather than introducing docs-owned dimensions.

## Accessibility

Give the group an accessible label when the relationship between controls is not already clear from surrounding content. Independent actions remain buttons. Single connected selection exposes radio-group/radio behavior; multiple connected selection exposes independent toggle-button pressed state.

Overflowed actions must remain reachable by keyboard and return focus predictably to the trigger when the overflow surface closes.

## Material fidelity and web adaptation

Material defines grouping, connected shape, action hierarchy, and expressive press treatment. Local `ResizeObserver` overflow and the browser radio/toggle semantics are web implementation details; they are not Material window-adaptive policy.
