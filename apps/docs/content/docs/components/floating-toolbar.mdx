Floating toolbars group contextual actions above content in a compact Material 3 Expressive surface. The public horizontal and vertical components own toolbar geometry and transition state; placement over the page and any adaptive choice of toolbar vs navigation surface remain composition-owned.

```tsx
import { HorizontalFloatingToolbar } from '@m3-ui/ui';

<HorizontalFloatingToolbar aria-label="Editor tools" expanded>
  <IconButton aria-label="Search">...</IconButton>
  <IconButton aria-label="Edit">...</IconButton>
</HorizontalFloatingToolbar>
```

## When to use

Use a floating toolbar for a compact group of contextual actions that should remain visually separated from underlying content. Use ordinary app bars or button groups when the actions belong in those persistent structures instead.

## Orientation and variants

`HorizontalFloatingToolbar` and `VerticalFloatingToolbar` expose the orientation directly and publish matching toolbar orientation semantics. Both support `standard` and `vibrant` Material visual variants.

## Expanded content and FABs

`expanded` explicitly controls whether `leadingContent` and `trailingContent` participate. Core children remain the central toolbar actions.

An optional FAB can be placed at the logical start/end for horizontal toolbars or top/bottom for vertical toolbars. The FAB remains an independent button action; the toolbar does not merge it into one composite click target.

## Exit state is explicit

Scroll-driven exit translation is supplied through public state; the component does not subscribe to document scrolling on its own.

```tsx
const state = createFloatingToolbarState(-64, offset, contentOffset);

<HorizontalFloatingToolbar
  aria-label="Scrolling tools"
  expanded={expanded}
  exitDirection="bottom"
  state={state}
>
  {actions}
</HorizontalFloatingToolbar>
```

`exitDirection` supports logical `start`/`end` as well as top/bottom, so direction-sensitive movement follows RTL. The surrounding application decides which scroll source updates the state.

## Accessibility

Every toolbar needs an accessible name describing the action collection. Children remain independently named buttons/toggles. When a toolbar surface is visually collapsed/hidden, hidden actions must leave the accessibility tree while any still-visible FAB remains reachable.

Do not implement a second roving-focus model unless the public toolbar contract explicitly requires it; ordinary toolbar children retain their own control semantics.
