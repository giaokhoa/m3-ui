A split button combines a primary action with a related secondary trigger. The two halves remain independent buttons: the leading side performs the primary action, while the trailing side can disclose or toggle a related choice.

</ComponentPreview>

```tsx
import { SplitButton } from '@m3-ui/ui';

<SplitButton
  leading="Create"
  trailing={<ChevronDownIcon />}
  onLeadingPress={create}
  onTrailingPress={() => setOpen((value) => !value)}
  trailingExpanded={open}
  trailingAriaLabel="Show create options"
/>
```

## When to use

Use a split button when one action is the clear default and a compact secondary trigger exposes closely related alternatives. Prefer two ordinary buttons when the actions are peers. Prefer a standard menu trigger when there is no meaningful default action.

## Menu ownership

`SplitButton` does **not** create, position, or manage a menu/popover. `trailingExpanded` only communicates that the trailing control owns an external expandable surface. The application composes that surface and owns open/close state, focus scope, positioning, and dismissal.

This boundary avoids inventing menu semantics when the public split-button component itself contains only two buttons.

## Variants and sizes

Available visual variants are `filled`, `tonal`, `elevated`, and `outlined`. Split-button sizes reuse the public Material button size family from extra-small through extra-large while applying split-specific connected shape geometry.

Choose the semantic variant/size rather than copying corner or spacing values into application CSS.

## Trailing state

Use `trailingExpanded` when the trailing action controls an expandable secondary surface. Use `trailingChecked` with `onTrailingCheckedChange` only when the trailing control is a real persistent toggle.

Do not use checked state merely to make a disclosure trigger look active: disclosure and pressed/toggled semantics represent different user contracts.

## Behavior and states

Both halves reuse the public Material button interaction engine. Press, hover, focus-visible, disabled, color, shape, and state-layer behavior stays local to each real button while the split geometry presents them as one Material control.

## Accessibility

Each half needs a meaningful accessible name. Visible leading text normally supplies the primary name; icon-only trailing disclosure controls should use `trailingAriaLabel`.

When the trailing half controls an external expandable surface, keep `trailingExpanded` synchronized with that surface's actual open state. Do not label the split container as an ARIA menu when it is not one.
